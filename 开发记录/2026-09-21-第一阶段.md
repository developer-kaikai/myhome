# 第一批开发记录

本批实现工程底座与日常身份链路；不代表首版全部完成。业务基线为需求 v1.5，视觉基线为 UI v5，技术设计同步至 v1.2。

## 已实现

- Maven 父工程及 common、core、ordering、party 四模块。common 为普通依赖 JAR，其余三个服务分别在 8082、8081、8083 运行。
- 27 张业务表的实体；V1 建表迁移保持原始中文表注释、字段注释、索引和约束。
- 统一响应、错误处理、请求 ID、OpenAPI、Redis 会话摘要及三服务共享鉴权。日常资格实时读取 MySQL，撤销不依赖缓存自然过期。
- 微信官方登录适配器、按稳定身份自动注册、默认昵称、个人昵称修改及版本冲突控制。缺少微信配置时明确返回 `WECHAT_NOT_CONFIGURED`，没有业务假登录接口。
- 主厨身份、日常密令 BCrypt 校验和 AES-256-GCM 加密；168 小时固定授权、连续 5 次错误锁定 10 分钟、修改密令保留旧凭证、独立撤销全部访客资格。
- 密令默认返回掩码元数据；查看或复制才获取明文，每次重新鉴权并审计。支持安全随机生成 6 位密令候选。
- 公共幂等组件与业务事务使用同一 MySQL 事务，支持重复请求重放、不同请求体拒绝以及失败回滚。
- 北京时间默认餐次、今天/明天和凌晨昨日宵夜、截止时刻排他判断；ordering 提供餐次查询接口。
- 原生 TypeScript 小程序、五 Tab、自定义导航、登录、个人昵称、日常密令以及个人中心内的主厨密令管理分包。
- 本地启动、独立容器集成测试、只读数据库检查及受控主厨绑定命令。

## 数据库变更

本机 `myhome` 已存在 27 张业务表。执行前与隔离库中 V1 的 `SHOW CREATE TABLE` 逐表比较，忽略自增计数后，字段、索引、约束和中文注释完全一致。核对结果为两家餐厅、两个季节品类、五条未启用通知模板，其余业务表为空。

在确认结构后，仅新增 Flyway V1 基线记录，不重复执行建表或种子数据；随后执行 V2 增量迁移：

- `openid`、`unionid` 改用大小写敏感排序规则，防止不同微信身份被错误合并。
- 昵称物理容量扩至 255 字符，业务上限仍为 20 个可见字符，容纳组合 emoji。

本地数据库现为 V2。两个主厨尚未绑定；待真实微信首次登录后按内部用户 ID 绑定。开发凭据保存在 `.local/`，已被 Git 忽略。

## 设计修正

微信官方 API 类型定义未包含 PATCH。小程序请求层及技术文档中的更新接口统一调整为 PUT，仍保留明确操作字段和乐观锁版本，避免类型强转掩盖平台不支持的方法。依据：[微信官方 API 类型定义](https://github.com/wechat-miniprogram/api-typings)。

技术设计中残留的 v3 宋体说明已改为 UI v5 系统无衬线字体。数据库 V1 保持不变，新增存储修正在 V2 迁移中。
