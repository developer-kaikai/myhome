| --- | --- |
| `FR-AUTH` | 准入控制与登录 |

| `FR-PARTY` | 聚会 |

### 1.2 术语表

| 术语 | 定义 |
| --- | --- |
| 主厨 | 某一餐厅的所有者与出品方。拥有该餐厅的后台管理权限,负责接单、做菜 |
| 顾客 | 在某一餐厅下单点餐的一方。同一人在对方餐厅中即为顾客 |

## 2. 产品概述

### 2.1 背景与产品定位

"我们的餐桌"面向情侣或小家庭这一极小范围的私密关系圈,把"今天谁做饭、做什么"这件日常琐事,包装成"两个人各自经营一家餐厅、互相点餐"的轻量仪式感产品。

产品并非商业餐饮系统,不涉及支付、配送、库存与营销;它的价值在于把家庭做饭这件事结构化、可记录、可回顾,并通过点餐、评价、统计等交互带来趣味性与情感留存。

### 2.2 核心设计理念:双餐厅对等模型

这是全系统最重要的结构性设定,后续所有模块的数据归属与权限判定都依赖它。

系统内存在两家对等的餐厅,分别由双方各自持有。每位用户具备双重身份:在自己的餐厅中是主厨,拥有菜单维护与接单权限;在对方的餐厅中是顾客,可浏览菜单并下单。因此"进入后台管理"这一动作,管理的始终是当前用户自己名下的那一家餐厅,而非全局。

由此推导出两条贯穿全文的规则:

1. **订单归属** — 每张订单必须明确归属到唯一餐厅,该餐厅的主厨是唯一的出品与接单方。
2. **统计区分** — 所有做饭统计、菜品热度、评价数据均按餐厅维度隔离计算,不跨餐厅混合。

> 对应《原始构思.docx》中"本点餐系统为双餐厅点餐,订单、统计等需要考虑如何区分"这一设计问题。

### 2.3 目标用户与角色

| 角色 | 说明 | 典型行为 |
| --- | --- | --- |
| 主厨(自有餐厅内) | 餐厅所有者 | 维护菜单与菜品、查看做法备注、接单、出品 |
| 顾客(对方餐厅内) | 下单方 | 浏览菜单、点餐、修改订单、评价菜品 |
| 聚会成员 | 受邀参与线下聚会的亲友 | 报名、认领采购物品、登记已购与金额 |
| 访客 | 未通过准入校验的微信用户 | 仅可见密令输入页 |

### 2.4 核心使用场景

**场景一:日常点餐。** 傍晚,A 打开小程序,首页看到"本周做饭 5 次""最受欢迎:番茄牛腩"。A 进入点餐,选择"她的餐厅",切到"晚餐",挑了番茄牛腩(微辣)×2、清蒸鲈鱼×1,备注"清淡一点,少放辣",下单。B 的微信收到订单提醒,进入主厨管理确认接单,并在菜品上点"查看做法"回顾步骤。晚上 21:00 订单自动完成,A 收到评价提醒,给番茄牛腩打了 5 星并留言"每次必point,汤汁拌饭绝了"。

**场景二:节日聚会。** 中秋前,A 创建聚会"中秋家宴",时间 9 月 17 日 17:00—22:00,地点"家里",通过微信把邀请链接发到家庭群。6 位家人报名后,大家在采购清单里添加大闸蟹、莲藕、月饼礼盒等物品,各自认领采购人。购买后点"已购买"并填入金额,系统自动算出人均 42 元。

## 3. 需求范围

### 3.1 本期范围

准入控制与微信登录、首页做饭统计与时令菜、双餐厅点餐、订单全流程与评价、聚会与采购分摊、个人中心、主厨后台管理、微信消息推送,以及节日主题装饰与多机型自适应。

### 3.2 明确不在本期范围

在线支付与资金结算(聚会采购仅做金额登记与人均计算,不做代收付)、外卖配送与地图定位、超过两家餐厅的多餐厅扩展、菜品营养成分与卡路里计算、社交动态与好友体系(成员邀请仅走微信链接)、数据导出与报表下载。

## 4. 角色与权限

### 4.1 准入控制(两道门)

小程序采用"准入校验 + 微信授权"双层控制,确保仅限私密范围内使用。

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FR-AUTH-01 | 白名单机制:后台可配置微信白名单(以 openid 标识)。白名单用户直接放行,永久有效,无需输入密令 | P0 |
| FR-AUTH-02 | 密令机制:非白名单用户进入时,必须先进入密令输入页,校验通过方可进入主流程 | P0 |
| FR-AUTH-03 | 密令校验通过后,为该用户签发访问凭证,有效期 7 天,凭证存于 Redis 并设置 TTL;过期后再次进入需重新输入密令 | P0 |
| FR-AUTH-04 | 密令输入页需支持错误提示(密令错误、密令为空);连续输错 5 次后锁定 10 分钟,防止暴力尝试 | P1 |
| FR-AUTH-05 | 微信授权登录:通过准入校验后,需完成微信授权(获取头像、昵称)才能使用点餐、订单、聚会等功能 | P0 |
| FR-AUTH-06 | 用户拒绝微信授权时,停留在授权引导页并说明用途,提供"重新授权"入口,不得进入主流程 | P1 |
| FR-AUTH-07 | 密令支持在主厨后台修改;修改后已签发的未过期凭证保持有效,不强制踢出 | P2 |

> 待确认:密令修改后是否需要使已签发凭证立即失效,取决于安全诉求,见 §11 开放问题 Q1。

#### 6.1.2 统计口径定义

口径必须唯一且明确,避免前后端理解不一致。

| 指标 | 口径 |
| --- | --- |
| 做饭次数 | 状态为"已完成"的订单张数;按订单计,一张订单含多道菜仍记 1 次 |
| 统计主体 | 双餐厅合计(即"我们家"本周做了几次饭),不区分由谁出品 |
| 最受欢迎菜品 | 周期内订单项数量求和最高的菜品;并列时取最近一次被点的菜品 |
| 周度周期 | 自然周,周一为起始日 |
| 月度周期 | 自然月 1 日至月末 |
| 年度周期 | 自然年 1 月 1 日至 12 月 31 日 |
| 已取消订单 | 不计入任何统计 |

> 待确认:做饭次数是否需要按餐厅拆分展示(如"我做了 2 次 / 她做了 3 次"),见 §11 开放问题 Q2。

## 10. 验收清单

以下为可直接转化为测试用例的关键验收项。

**准入与登录**

- [ ] 白名单微信用户可直接进入,不出现密令页
- [ ] 非白名单用户必须输入正确密令才能进入
- [ ] 密令校验通过后 7 天内免密进入,第 8 天需重新输入
- [ ] 连续输错 5 次后锁定 10 分钟
- [ ] 拒绝微信授权时无法进入主流程

**首页**

- [ ] 周/月/年切换后做饭次数、最受欢迎菜品、趋势图同步刷新
- [ ] 做饭次数与已完成订单张数一致,已取消订单不计入
- [ ] 时令菜同一天内保持不变,次日更新
- [ ] 当前月份无季节限定菜品时时令卡片整体隐藏

**点餐**

- [ ] 两家餐厅名称与封面正确取自各自主厨的后台配置
- [ ] 切换餐厅后已选菜品互不干扰
- [ ] 默认餐次与当前时间匹配
- [ ] 列表页简介超 10 字截断
- [ ] 下单次数前 5 的菜品显示 HOT 标签
- [ ] 季节限定菜品仅在配置月份出现
- [ ] 配置了规格的菜品未选规格时无法加入订单
- [ ] 同菜品不同规格作为独立订单项存在
- [ ] 同一餐厅同日同餐次多次点餐归并为一张订单
- [ ] 订单项正确显示点餐人
- [ ] 数量减至 0 时订单项移除
- [ ] 未选菜品时结算栏不可点击

**订单**

- [ ] 下单后主厨微信收到提醒
- [ ] 追加、修改、取消均触发主厨提醒
- [ ] 早/午/晚/宵夜订单分别在 11:00 / 15:00 / 21:00 / 次日 02:00 自动完成
- [ ] 未接单订单到点同样自动完成
- [ ] 自动完成后点餐者收到评价提醒
- [ ] 已完成与已取消订单无修改入口
- [ ] 仅能看到本人参与的订单,直接访问他人订单被拒绝
- [ ] 评价 1—5 星提交后菜品平均星级与评价数实时更新
- [ ] 评价同时展示在订单详情与菜品详情

**聚会**

- [ ] 创建聚会时结束时间早于开始时间被拦截
- [ ] 分享链接卡片正确展示主题、地点、时间区间
- [ ] 采购人下拉框仅列出已报名成员
- [ ] 点击已购买并输入金额后人均费用自动更新
- [ ] 成员数变化后人均费用同步重算
- [ ] 删除采购物品后人均费用重算
- [ ] 金额输入负数或超过两位小数被拦截

**个人中心与主厨后台**

- [ ] 非主厨看不到主厨入口
- [ ] 主厨仅能管理自己名下餐厅
- [ ] 顾客侧任何位置都看不到"做法"按钮与做法备注
- [ ] 餐厅名称与封面修改后点餐页同步生效
- [ ] 上传超过 5MB 的图片被拦截并提示
- [ ] 菜品图片支持 1:1 裁切
- [ ] 季节限定品类不可删除、不可重命名
- [ ] 品类下有菜品时删除被拦截
- [ ] 规格默认值在下单页正确预选
- [ ] 确认接单后订单状态变为已接单

**全局**

- [ ] 各列表页空态、加载态、错误重试均有对应展示
- [ ] 节日区间内自动切换主题装饰,区间外恢复默认
- [ ] 主题素材加载失败降级为默认主题且不影响页面
- [ ] 主流机型下页面无错位、无内容截断、底部安全区正常

## 11. 开放问题

以下问题需在开发启动前确认,均会影响实现方案。

| 编号 | 问题 | 影响范围 | 建议方案 |
| --- | --- | --- | --- |
| Q1 | 密令修改后,已签发的未过期凭证是否立即失效? | 准入控制 | 建议不强制失效,保留 7 天自然过期,体验更平滑 |
| Q2 | 首页做饭次数是否需按餐厅拆分展示? | 首页统计 | 建议首版按双餐厅合计展示,保留后续拆分空间 |
| Q3 | 多人共同点餐是否需要实时同步? | 点餐系统 | 建议首版采用进入页面/下拉刷新拉取最新,不引入长连接 |
| Q4 | 已接单订单被修改后是否回退至待接单? | 订单状态机 | 建议回退并推送变更,确保主厨知晓最终菜单 |
| Q5 | 菜品评价是否设置时效上限? | 评价 | 建议不设硬限制,但超过 7 天不再推送提醒 |
| Q6 | 菜品与背景图片的存储方案? | 图片存储 | 需在技术设计阶段确定(对象存储 vs 本地静态目录),并明确缩略图策略 |
| Q7 | 是否支持双方之外的第三人参与日常点餐? | 点餐权限 | 原始构思提到"支持多人同时点餐",建议首版限定为已授权的家庭成员范围 |
| Q8 | 用餐人数与菜品数量是否需要联动校验? | 下单 | 建议不做强校验,仅作记录 |
